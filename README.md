## What the original book claims

Conitzer asked whether an exact Bayes-Nash equilibrium (BNE) of a Bayesian simple security game can be computed in
polynomial time. The book does not settle this; it places the problem between two known problems.

* **Lower bound:** exact BNE search is ARRIVAL-hard, already with one defender resource and defender payoffs 0/1
  (Thm. 4.1). For the shorter construction of Appendix C, Lean checks correctness and the size bounds only;
  that the reduction runs in polynomial time is checked by AI referees, not by Lean.
* **Upper bound:** exact BNE search reduces many-one to one P-matrix LCP and lies in UEOPL (Section 5.2 and
  Thm. 5.28). Lean checks the correctness of the Section 5.2 reduction for 0 < r < n in marginal coordinates;
  `lean/README.md` lists what it does not cover, including the UEOPL step.
  The market route also recovers an integer switching-flow certificate for S-ARRIVAL (the search
  version in Gärtner et al., Definition 13) from one P-LCP solution, as shown after Corollary 5.9.
* **Structure:** the problem is polynomial-time Turing equivalent to an affine matching market (Chapter 3).
* **Algorithms:** an exact algorithm with L^O(sqrt(min(m,n))) bit operations (Section 5.5); the Li-Conitzer-Korzhyk
  algorithm takes exponentially many steps on explicit games (Chapter 6).

Where to start: the preface and Chapter 1 of `main.pdf` (Section 1.4 explains the ideas without formulas), then
Appendix C (the shortest complete hardness proof) and Section 5.2 (the main upper bound).

## Checking the Lean proofs

```
cd lean/project
lake exe cache get && lake build    # Lean v4.36.0 and Mathlib, pinned by lean-toolchain and lake-manifest.json
```

The build ends by printing, for each main theorem, the axioms it uses; expect only `propext`, `Classical.choice`
and `Quot.sound` (`lean/build-output.txt` is one such build). `lean/README.md` maps each Lean theorem to the book.

**What Lean does not show: polynomial running time.** Lean proves correctness (for example, every rational BNE of
the constructed game decodes to the right ARRIVAL answer) and size and bit-length bounds. It proves no
running-time bound for Red or Dec. Their Lean definitions are specifications: the preprocessing's reachability
test `liveWithin`, evaluated by its own recursion, can take time exponential in n. The project also defines a
stage-by-stage version `liveWithinFast` (O(k n^2) operations), proves the two equal (`liveWithinFast_eq`) and
makes compiled code use it (`@[csimp]`), so the executable Red is polynomial in practice; but that Red and Dec
run in polynomial time is a claim of the book checked only by AI referees.

## Scope (read before relying on anything here)

* The proofs were produced by AI and refereed by AI referees. No human expert has verified any of them.
* The code checks are exact (rational arithmetic, z3 over linear real arithmetic) but cover only small
  instances. For general sizes every result rests on its proof.
* A few z3 checks use a fixed timeout and can return `unknown` instead of `unsat` under machine load
  (UEOPL contraction search, `ueopl_seed3` and `ueopl_seed4`; see `code/REPRODUCTION.md`). No run found
  a violating pair.
* Lean: the ARRIVAL-hardness theorem, in the form of the shorter proof (Appendix C), is machine-checked for correctness:
  `lean/project`, theorem `Bssg.main_proof`; `BssgProofs/Final.lean` checks that its statement is exactly the
  specification `main` and prints its axioms (only `propext`, `Classical.choice`, `Quot.sound`). Not formalized: a polynomial running-time bound for Red and Dec (see "What Lean does not show"
  above; the size and bit-length bounds are proved: `red_bits`, `red_descBits`), the original
  Chapter 4 construction, and Chapter 6. Parts of Chapters 3 and 5 are formalized as well (the direct
  P-LCP reduction of Section 5.2, the market LCP of Section 5.1, the market-to-game embedding and the
  contraction of Section 5.3); `lean/README.md` lists exactly what is and is not covered. Lean certifies the theorem about the project's own
  definitions; read `lean/project/DEFINITIONS.md` to audit them against the paper.
