# Submission: Bayes-Nash equilibrium in Bayesian simple security games

Everything here (mathematics, Lean formalization, code, checks and text) was generated by AI agents. Vincent Lin (<mailto:vincent2@alumni.cmu.edu>) coordinated the agents and wrote none of the content.

## What is claimed

Conitzer asked whether an exact Bayes-Nash equilibrium (BNE) of a Bayesian simple security game can be computed in
polynomial time. The book does not settle this; it places the problem between two known problems.

- **Lower bound:** exact BNE search is ARRIVAL-hard, already with one defender resource and defender payoffs 0/1
  (Thm. 4.1). For the shorter construction of Appendix C, Lean checks correctness and the size bounds only;
  that the reduction runs in polynomial time is checked by AI referees, not by Lean.
- **Upper bound:** exact BNE search reduces many-one to one P-matrix LCP and lies in UEOPL (Section 5.2,
  largely Lean-checked, again without running time; Thm. 5.28).
- **Structure:** the problem is polynomial-time Turing equivalent to an affine matching market (Chapter 3).
- **Algorithms:** an exact algorithm with `L^O(sqrt(min(m,n)))` bit operations (Section 5.5); the Li-Conitzer-Korzhyk
  algorithm takes exponentially many steps on explicit games (Chapter 6).

**Where to start:** the preface and Chapter 1 of [main.pdf](main.pdf) (Section 1.4 explains the ideas without formulas), then
Appendix C (the shortest complete hardness proof) and Section 5.2 (the main upper bound).

## Running the code

Pinned versions are in [code/requirements.txt](code/requirements.txt) (CPython 3.12.11, z3-solver 5.4.1.0; numpy and scipy only
for one floating-point MILP cross-check).

```bash
cd code
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
PY=$PWD/.venv/bin/python ./run_quick.sh    # 56 checks, about 4 min on a quiet machine
PY=$PWD/.venv/bin/python ./run_full.sh     # all 124 checks, about 4-7 h
```

## Checking the Lean proofs

```bash
cd lean/project
lake exe cache get && lake build    # Lean v4.36.0 and Mathlib, pinned by lean-toolchain and lake-manifest.json
```

The build ends by printing, for each main theorem, the axioms it uses; expect only `propext`, `Classical.choice`
and `Quot.sound`. [lean/README.md](lean/README.md) records that output and maps each Lean theorem to the book.

**What Lean does not show: polynomial running time.** Lean proves correctness (for example, every rational BNE of the
constructed game decodes to the right ARRIVAL answer) and size and bit-length bounds. It does not prove that
`Red` or `Dec` run in polynomial time. The Lean definitions of `Red` and `Dec` are specifications, not efficient code: as
written, the preprocessing’s reachability test `liveWithin` explores both exits recursively and takes time
exponential in `n` in the worst case. The book’s `Red` computes the same set of vertices by ordinary graph search in polynomial time;
that this agrees with `liveWithin`, and all running-time claims, are checked only by AI referees.

## Scope (read before relying on anything here)

- The proofs were produced by AI and refereed by AI referees. No human expert has verified any of them.
- The code checks are exact (rational arithmetic, z3 over linear real arithmetic) but cover only small
  instances. For general sizes every result rests on its proof.
- A few z3 checks use a fixed timeout and can return `unknown` instead of `unsat` under machine load
  (UEOPL contraction search, `ueopl_seed3` and `ueopl_seed4`; see [code/REPRODUCTION.md](code/REPRODUCTION.md)). No run found
  a violating pair.
- Lean: the ARRIVAL-hardness theorem, in the form of the shorter proof (Appendix C), is machine-checked for
  correctness: `lean/project`, theorem `Bssg.main_proof`; `BssgProofs/Final.lean` checks that its statement is
  exactly the specification `main` and prints its axioms (only `propext`, `Classical.choice`, `Quot.sound`). The size
  and bit-length bounds are proved (`red_bits`, `red_descBits`). Not formalized: polynomial running time (the Lean
  `Red` is not polynomial-time code as written; see above), the original Chapter 4 construction, and Chapter 6. Parts
  of Chapters 3 and 5 are formalized as well (the direct P-LCP reduction of Section 5.2, the market LCP of Section
  5.1, the market-to-game embedding and the contraction of Section 5.3), also without running time;
  [lean/README.md](lean/README.md) lists exactly what is and is not covered. Lean certifies the theorems about the project’s own
  definitions; read [lean/project/DEFINITIONS.md](lean/project/DEFINITIONS.md) to audit them against the paper.
